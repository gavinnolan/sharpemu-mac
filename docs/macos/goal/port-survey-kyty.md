Caveats that apply to every number below:
1. Platform: all Kyty numbers are Vulkan on an RTX 5090 / i9-14900K (and an RTX 3080 8 GB laptop), CPU-bound on the translation thread, at 2560x1440 render. We are Metal on Apple Silicon at 1080p. Take the PS5/DS semantics and the shape of each finding, not the fps deltas.
2. Game version: Kyty targets PPSA01341 v01.007.000/01.005.000. Guest addresses and shader hashes quoted in their docs do not apply to our v01.004.000 and must be re-derived (masked signatures).
3. "our equivalent" was decided by `rg` over `src/` by the survey agents plus spot checks by the orchestrator. ALREADY = equivalent present; DIFFERENT = we solve it another way; MISSING = no hit for the relevant identifiers. "unverified" = not proven by reading alone. Items marked [V] were re-verified by hand when this report was assembled.
4. Policy: GOAL.md forbids title-specific hacks. Items 2, 14 and 35 are the game's own documented settings or generic detectors, not output-changing patches; the decision and its reasoning must be recorded in the phase report.
5. Commit links: chenxiao07 = `https://github.com/chenxiao07/KytyPS5/commit/<hash>`, main = `https://github.com/KytyPS5/KytyPS5/commit/<hash>`. All hashes below were checked to exist in the local clones. Docs cite stale hashes (history was squashed); the hashes here were re-resolved with `git log`.

## 2. (b) Top 15: semantics to port

Order is the recommended attack order for the GOAL (cheap and verified-missing correctness first, then the memory-phase levers, then the perf levers that need measurement). Each paragraph states the PS5/engine behaviour, so the port is a re-implementation from semantics.

**1. START_INST_LOC (table item 1, Phase 4).** On RDNA2 the indirect draw packets (DRAW_INDIRECT, DRAW_INDEX_INDIRECT and the multi forms) carry two register locations, one for BASE_VTX and one for START_INST. The command processor reads the draw-argument block (index count, instance count, start index, base vertex, start instance) and writes the start-instance dword into the user SGPR that the packet names. The hardware's instance-id VGPR counts from zero for the draw; the shader adds the SGPR itself. Chen's DS notes say DS names SPI_SHADER_USER_DATA_GS_2 on about 95% of its indexed indirect draws and that the dword is packed: the low half is the instance base added to the instance id, the high half is a per-object vertex offset. We drop the two location dwords at `GpuCommandInterpreter.Draws.cs:303-313`, and Metal's `[[instance_id]]` is documented to include the base instance (confirm with a one-draw test), so a shader doing `(sgpr & 0xffff) + instance_id` sees base instance twice or a stale SGPR. To port: record the named register in the draw, include it in the vertex-stage specialization key, deliver the argument dword to that SGPR per draw (for GPU-resolved indirect draws this must be read on the GPU), and set the translated instance VGPR to `instance_id - base_instance` (Metal exposes `[[base_instance]]`). Kyty reports a 1.5-2.5% fps cost and fixed whole missing objects. Main's independent implementation (9f83fd5f) confirms the semantics. Verify with a one-draw test before any game run; then check Boletaria 1-1 brazier and Latria cell hall against the reference video.

**2. Engine console variables through the package args file (table item 2, Phase 3).** The Bluepoint engine executes each `+name=value` line of the package's command-line file at boot (read once, so changes cannot be made at run time). `doIndexBufferCulling=false` disables the pre-draw compute pass that culls triangles for every virtual-geometry ("XPR") object; with it off the GPU draws the unculled triangles, the output is visually identical (animation/fog noise only), about 2800 dispatches per frame disappear at 1-1, and the guest stops issuing about a third of its per-frame GPU-result reads (the index-count==0 checks on the 20-byte indirect arguments). Kyty serves a temporary modified copy of the file when the game opens it; the real file is untouched. In our dump the file is `PackageCmdLineArgs.txt` (mixed case; the engine reads it as `$/packagecmdlineargs.txt`) and already holds one line, so the overlay must append, keep stat/size/read consistent, and resolve case the way our file layer does. Tension with GOAL.md: this is the game's own supported setting rather than an emulator patch, and it changes the amount of GPU work, not the picture; record that in the phase report. The same mechanism carries other convars worth one batch each: `sound_enableAmbisonics=false` (item 25) and `gameMinDeltaTime` (only matters above 60 Hz). Measure on Metal: Apple GPUs are far weaker than a 5090 so the extra triangles may give back part of the CPU saving (Kyty: GPU 60% to 71% busy, still net positive).

**3. Hold streamed textures from BASE_LEVEL (table item 3, Phase 1).** DS streams textures smallest-mip-first and its T# BASE_LEVEL moves down as larger levels arrive. In the RDNA2 64 KiB tiled layout the mip tail comes first and the levels after it run from smallest upward, so levels k..N of a 2D, single-layer, tiled, metadata-free texture sit at the same addresses as a smaller texture of size>>k with fewer levels. The emulator can therefore allocate only levels k..N and re-create (and re-upload) the image larger when a lower level is first sampled. Conditions Chen applied: sampled use, 2D, one layer, tiled, no metadata, no image of the whole texture already registered; levels without tiled layout keep the whole chain. At 1-1, 495 of 913 textures were never sampled from level 0; those larger levels were 1.7 GB of 3.9 GB of textures (4232 to 2560 MiB). Our `ImageRequestBuilders.Texture.cs:297` sizes the image for all levels and our image budget (`MetalImageCache.cs:169-181`) is 3-8 GiB shared with guest RAM, so on unified memory this is a direct footprint lever. Port the addressing equations from the AMD addrlib (`gfx10addrlib.cpp`, section 4) and the SDK `texture.cpp`, not from Kyty; unit-test per format. Chen gated it below 12 GB of video memory; we should decide by our unified budget, not a fixed threshold.

**4. Age-based retirement (table item 4, Phase 1).** A texture/buffer collector that only runs near the budget never runs on a machine with headroom, yet streamed textures keep their images and page watchers after the game reuses that memory, so every later CPU write to the reused pages faults and the game slows the longer it runs (Kyty: three loops of the same route lost 12 fps; VMA grew by 3 GB in 12 minutes). Port the policy: each flip, retire a bounded number of images unused for about 1200 flips (skipping GPU-only bytes, depth/stencil associations and anything used in the last frames), and retire idle buffers by wall time (30 s, 10 s with up to 256 per flip under critical pressure; never a buffer used in the last 120 flips; 600 flips was too short, a turned camera re-registered everything and cost 7 fps in Latria). Our `MetalImageCache.Tracking.cs:431-478` is budget-triggered only. This is the cheapest way to meet the Phase 1 "no growth over 30 minutes" exit, and it also removes write faults (item 15).

**5. File-open follow-ahead (table item 5, Phase 2).** DS opens roughly 28.5K files lazily, on first APR read, on a single game file thread, in nearly the same order each run (31,390 APR reads of 28,528 files; first open median 0.9 ms, p90 11 ms, max 310 ms on Windows). Kyty records the order of first opens per title and version, and on every open (or first read after an ahead-open) hands the next 256-1024 recorded paths to a pool of low-priority threads that open them into the kept-handle cache; a release can ship the recording (file names only) so even the first launch benefits. Result: 1-1 loading fog 95-110 s down to 17-20 s with 16 helper threads and a window of 1024. On macOS there is no antivirus open hook so expect a smaller win, but our own code comment says DS pays about 9k cold opens per boot on the external volume, and our LRU cap (16384) is below the distinct file count so it may thrash during a level load. Do: measure with FileIoProfile; raise or remove the cap; add the record-and-follow thread pool; key the recording by title+version.

**6. Fiber stack headroom (table item 6, Phase 3).** DS's job system (a Bluepoint "BPE Job Fiber") creates 128 fibers with 16 KiB stacks and 32 with 64 KiB stacks, laid end to end, sized for a PS5 where no host code ever runs on them. Chen painted the stacks: the guest alone reaches 13.6 KiB of a 16 KiB stack, and with host frames (fault dispatch, an HLE function with a 40 KiB frame) up to 45-55 KiB, spilling into the neighbour's top. Every crash on his record (assert int 0x41, garbage `this`, corrupted SRW wait block, sceFiberSwitch storing 0x17, execution of a host-heap address, a JobSystem hang at the title screen) had rsp within about 3 KiB of a fiber-stack top; a private stack per fiber (game size plus 256 KiB above a guard page, game context keeps only the magic) removed all of them in two 16-spawn world tours. Our HLE already switches to a host stack, but the fault bridge installs handlers without SA_ONSTACK, so the kernel pushes the signal frame (siginfo plus ucontext, larger with Rosetta/AVX state) onto the guest fiber stack. Do first: paint-stack watermark logging per fiber in a short harness run to learn whether we are near the limit; if so, allocate private fiber stacks and give the guard page a real report path.

**7. Compute dispatch barriers (table item 7, Phase 3).** DS orders its compute work with explicit PM4 sync (ACQUIRE_MEM, WAIT_REG_MEM, EOP/RELEASE_MEM, partial flushes) and emits about 4250 dispatches per frame (about 85% in runs of the same shader). Between sync points consecutive dispatches have no dependency the host must enforce, so a pending barrier can be carried across consecutive dispatches and drained only by uploads, transfers, draws, submissions and guest sync events; full guest barriers subsume it. Chen measured +12.7% (the largest early win) and 7470 to 3087 barriers per frame (33.9 to 40.6 fps), but on an RTX 3080 laptop the chain produced device hangs in roughly half of 10-minute tours (workaround: fence everything, costing 25-37%), later reduced by an unrelated register-pressure fix; the hang was never root-caused. We emit a compute-encoder memory barrier after every dispatch on a serial encoder. A Metal port means concurrent dispatch type with explicit barriers at guest sync points, plus a runtime kill switch and an all-output-words comparison test (as Chen did), and only after the cheaper items are measured. It is an assumption about DS, not about arbitrary titles: the doc says so explicitly, and that bears on GOAL's no-title-specific rule, so gate it on the observed PM4 pattern (explicit sync between dependent groups) rather than a title id.

**8. Fail soft on stale state (table item 8, Phase 3).** While an area loads, DS leaves descriptors and register state the hardware never consumes: T# slots with DCC address 0 or an illegal mip range, a colour target with COLOR_INVALID format (seen at the pause menu after several world switches), Z-info with EXPCLEAR or partially-resident bits. Real hardware ignores them. Rules to port: a COLOR_INVALID (format 0) target is simply not drawn to; a sampled or storage view whose T# cannot be decoded binds a null image and logs once; a draw or dispatch whose resource tables cannot be evaluated is skipped; EXPCLEAR/partially-resident depth flags are accepted because our host depth attachment is always fully expanded and resident. Our verified fatal sites: `ImageRequestBuilders.ColorTarget.cs:128-143` leading to `GuestSurfaceFormats.cs:68`, `ImageRequestBuilders.DepthTarget.cs:156-158`, `ImageDescription.cs:379-397`. Chen saw "invalid DCC metadata" a few times per session in DS. Start with these three and then audit the rest of the roughly 200 GpuFatal sites for ones a stale descriptor can reach.

**9. Causal delay probe (table item 9, Phase 3).** Not a code port but the method that makes the remaining phases honest. Inject a spin of known length (say +1.2 ms per frame) at a candidate site (per-dispatch encode, readback wait, flip) and read the frame-time slope: a slope near 1 means the site is on the critical path, near 0 means it overlaps. In DS, +1.2 ms on the graphics-queue translation gave +1.06-1.23 ms frame time while the same delay on the async-compute dispatches gave +0.06 ms, which explained why saving 0.8 ms in places gained nothing. Combine with: same-process alternating A/B using a runtime toggle (cross-session noise was 1-3 fps), total frames over total time rather than window means, screenshot on every run (a fast-path regression hid black triangles for days), and an "unsafe ceiling first" step (skip the work entirely to bound the possible gain). Fits GOAL's run budget: one probe build, one run.

**10. Fills as clears (table item 10, Phase 3).** DS clears render targets and volumes with a compute shader that fills repeating dwords, in pieces that span several images or write 64/128-bit texels (32_32_32_32 UINT targets, an 18 MiB R16G16B16A16F froxel volume). If the fill must match exactly one image with 32-bit texels, everything else runs as a buffer dispatch that marks every aliased image "written by buffer" and forces a detile from guest memory. Port: treat the fill as a buffer fill and also let each overlapping image remember "filled with this value"; an image whose every buffer write since upload was one covering fill is initialised with a clear (decode the fill word into wider texel formats; NaN/inf patterns keep the dispatch). Kyty: Stonefang 113 MB of detiled zeros per frame fell to 8 MB, 2-3 went 37.6 to 43.7 fps, the Boletaria froxel fill removed 41.8 MB/frame of detiles. We fold fills only over one exact cached image, so this extends `MetalRenderHost.KernelFills.cs` and `BoundedFillDetector`.

**11. Texture-pool layer views (table item 11, Phase 1/3).** DS's streamed texture pool is a single T# of about 1500-1700 BC 1024x1024 layers (1.3-1.8 GB) sampled through views that start at later layers and cover a few; the layer range grows during streaming (1777 to 3633 layers in one session; 7745 for a 512 pool). Treating each distinct view as its own image uploaded each growth whole beside the old copy; Kyty reached 13 GB of video memory and 3.2 s frames on one GPU. Port: images of the same shape on the same slice grid hold the same texture at the same bytes, so serve every view from one holder, grow by a GPU copy of the old layers plus an upload of only the new ones, and hold only the used layers for views that start past layer 0 (608 MiB instead of 1553 MiB at 4-2). Needs a trace of a DS pool T# sequence on our path first to see whether we really duplicate arrays; `MetalImageCache.cs:1444` releases subsets rather than sharing.

**12. Partial refresh (table item 12, Phase 3).** DS writes texture mips into guest memory while draws already sample the texture, and its shadow pool (80 layers of 1024x1024 D32, 320 MiB, sparse) receives shadows in a few layers while the streamer tiles textures into the free ones from the CPU. Refreshing whole images on each use or depth binding moved about 1 GB in three frames when turning to an unseen view. Rules: refresh only dirty tiles of the levels the view reads (plus the mip-tail page), keep GPU-written bytes on a partial unmap or CPU write, upload whole depth layers only where dirty, split images both CPU- and GPU-written into the CPU-written and GPU-written subranges. Our `TryRefreshDirtyRun` handles one run and refuses beyond half the image; multi-range and level-restricted refresh are the gap. Kyty's Shrine-entry worst frame fell from 746 to 232 ms.

**13. Partial unmap keeps neighbours (table item 13, Phase 3/4).** A guest `munmap` of part of a mapping, MAP_FIXED over part of one, or freeing part of direct memory must change only the affected pages. If the whole host view is torn down and rebuilt with default protection, pages the GPU tracker had write-protected lose protection, later CPU writes never fault, and the GPU keeps stale data: Kyty's "out-of-body" bug (the character model frozen in place while the player moves an invisible character), and a fatal "required direct-backing write failed" because the pages were briefly absent. DS does partial unmaps constantly while streaming (texture-pool layers). macOS mmap/MAP_FIXED handle partial ranges natively, so our risk is narrower than on Windows, but two things need an audit: that the tracker protection is re-applied to surviving pages after a partial replace, and that no window exists where a live range is PROT_NONE or unmapped for another guest thread (main's 46900d80/b2fdad9e fix exactly that on POSIX). Static read of `GuestImageWriteTracker` and the host Memory layer first.

**14. Memmove compare-before-write (table item 14, Phase 3).** DS moves 4.2-5 MB per frame in memmoves of at least 256 KiB into GPU-cached memory, and 64-80% of the destination pages already contain the source's bytes. Writing the whole span marks every page CPU-dirty, which re-uploads it and re-arms write protection (and a later fault). Kyty compares non-overlapping moves page by page, writes only differing pages (plus GPU-written pages whose host bytes are stale) and hands a whole-range host write over without reading the GPU copy back first. Result: uploads 18.3 to 14.3 MB/frame, +1.7% fps. On unified memory the upload is cheaper, but each avoided dirty page also avoids a re-protect and a likely fault, which matters under Rosetta fault costs. First confirm whether DS calls libc memmove through our HLE or a statically linked copy.

**15. Sequential write-fault window (table item 15, Phase 3).** GPU-cached guest memory is write-protected; each guest write faults and invalidates a window. Telemetry in DS: about 1000 window faults per frame at 1-1, 83-88% on a window that already faulted within 100 ms, 31% sequential (previous window faulted under 2 ms earlier). When a thread faults on the window directly after its previous one within 2 ms, invalidate the next 64 KiB at once. Kyty: faults -13.6%, protect calls -5.8%, 1% low +3.8% on the 1-1 route; leaving hot pages writable was a disaster (13 MB to 25.8 GB of uploads per frame, 5 fps). Count our faults per frame first (a Mach exception under Rosetta costs more than Windows SEH, so the per-fault saving may be larger); with item 4 retiring idle watchers, items 4, 14 and 15 together attack the same fault budget.

(Items 16-42 in the table follow in the same attack order; of those, the next most valuable are the int 0x41 skip, VRSQRTPS deterministic rewrite (needed before the Rosetta sunset), the VideoOut resolution class, the AMPR read-through and WriteAddress sizing, the persistent pipeline store, and the ambisonics front component.)

## 4. (d) Skipped items (one line each)

- Native XPR record/replay, table-mode XPR snapshots, GPU-driven XPR (CX [7eec0198](https://github.com/chenxiao07/KytyPS5/commit/7eec0198), [54e68a69](https://github.com/chenxiao07/KytyPS5/commit/54e68a69), `docs/NATIVE-XPR-*.md`, `GPU-DRIVEN-XPR.md`): Vulkan CPU-translation-bound design (24.85 to 30.93 fps, weeks of work) that only pays if our per-draw Metal encode is dominated by resource-table evaluation, which is unmeasured; revisit after a profile, not before. ## 5. Appendix: DS facts learned and dead ends (from chenxiao07 docs, for the phase plans)

DS facts (Windows/Vulkan numbers, version 1.07; re-derive addresses for v01.004.000):
- Frame structure at Boletaria 1-1 standing: ~6,790 indexed indirect draws, ~1,020 ordinary draws, ~4,250 compute dispatches, ~23 graphics command buffers; graphics DCBs carry no direct SET_CONTEXT_REG, all state arrives through SET_{SH,CONTEXT,UCONFIG}_REG_INDIRECT tables and each DCB starts with a WAIT_REG_MEM; ~11 top-level WAIT_REG_MEM per DCB (21% already satisfied, 66% by the same DCB's own writes, 8-10% by compute queues, 0% by CPU writes).
- The guest reads GPU output ~62 times per frame (539 KB): particle stats ~53%, XPR index culling ~32%, GPU collision (foot IK) ~5%, auto exposure ~2%. Gameplay logic never reads GPU results. A frame allocator reuses the same pages as a CPU linked list one frame and GPU output the next, so handing the guest "old data" crashes (0x8120b8).
- Frame-start chain: previous frame's GPU tail (~4.6 ms) then culling submit, culling translation and GPU lag, then the main submit: mean 10.2 ms and correlated 0.69 with frame length. The async culling chain waits on a frame label on the PS5 too, so previous-tail/next-culling overlap is impossible on real hardware; a separate async queue gave at most 0.6 ms.
- CPU-only guest layer runs ~96-100 fps with rendering skipped (10.4 ms/frame); the render/translation side is the limiter at ~30-45 fps in Kyty. The game's clock is a 60 Hz virtual vblank. Worker spin is a compiled behaviour (CPU 1338% to 388% with a sleeping idle poll).
- Memory: guest direct memory 13.5 GiB; ~17,000 VMAs from protection-split mappings; level entry streams 1-1.25 GB per frame then a ~9 s burst; mappings grow 9.4K to 51K over 24 loads; process ~20 GB while a save loads, ~4 GB in play on Windows; ~250K files resolved by APR at start; 1330 of 38,925 AT9 files are 16-channel third-order ambisonics.
- Static content: ~20.6K programs (10.7K compute, 9.5K particle variants), ~50K pipelines; wave64 emitted twice on 32-wide GPUs made compile 2.3x slower; shaders differ between game versions (only 10 of ~21K identical between 1.05 and 1.07).
- Streaming memory: DS writes memmoves of >= 256 KiB (4.2-5 MB/frame); its draws sample textures while their mips are still being written; shadow pool 80 layers of D32 1024x1024 (320 MiB) whose free layers the texture streamer borrows.

Dead ends measured by Chen (do not retry without a new argument; all Vulkan/RTX 5090 CPU-bound numbers): per-draw PBR prep reuse (-2.3% to -3.5%, 91-93% hit rates but more bookkeeping than savings); repeat-draw fast paths (6 variants, all slower); native compute/shadow/culling pass replacement (-10% to -35%); render-thread frontend/backend split (flat); speculative parallel DCB translation (-15%, ~4% of DCB start states match); latent/snapshot readbacks (-1.25 fps to -8%, plus a crash); zero-copy host-memory alias (image allocation OOM); GPU in-place table reads (+4 ms GPU, 7.6% of slots rewritten between translate and execute); leaving re-faulting pages writable (13 MB to 25.8 GB of uploads per frame); strict thread pinning (28 fps); skipping all barriers as an unsafe ceiling (+1% only); patching the game's fps setting (caps nothing); a 240 Hz vblank (breaks the game clock); pipeline libraries/shader objects/DX12 (<= 3%); instrumentation itself (+32%: 136,325 scopes at ~69 ns). Process lessons: "hit rate" and "cost coverage" are not savings; always compare screenshots, not just fps; cross-session fps drifts 1-3, only same-process A/B counts.
