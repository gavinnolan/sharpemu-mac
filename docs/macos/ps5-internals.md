What the query APIs return in practice:

- `sceKernelGetDirectMemorySize()` returns the title's total direct budget (~12 GiB on base hardware, see above). It is a constant for the process and does not shrink as you allocate. Sony samples pass it as the search end of every allocation. SAMPLES: `system/api_apr/main.cpp:52`, `graphics/tutorial_asset_streaming/lib/source/core_streamer.cpp:238`. The header spells it `SCE_KERNEL_MAIN_DMEM_SIZE`.
- `sceKernelAvailableDirectMemorySize(start, end, alignment, &startOut, &sizeOut)` returns the largest free physical extent inside the search range that satisfies the alignment (the semantics are those of a first-fit search). SDK: `sys/dmem.h`. [SDK signature, extent semantics from KYTY `KernelAvailableDirectMemorySize`, `src/kernel/memory.cpp:2641` and `PhysicalMemory::Available` at 1126: [Emu]].
- `sceKernelAvailableFlexibleMemorySize` and `sceKernelConfiguredFlexibleMemorySize` return remaining and total flexible budget. SDK: `kernel/memory.h`. When the budget is exhausted `sceKernelMapFlexibleMemory` fails with ENOMEM (AnyPS5 #4508 log: "flexible memory exhausted"). Real titles probe the flexible budget by mapping in a loop (shadPS4 comment in `src/core/memory.cpp`, https://raw.githubusercontent.com/shadps4-emu/shadPS4/main/src/core/memory.cpp). [Emu]
- The PS4 constants for comparison: base 5248 MB total, Pro 5888 MB, flexible 512 MB (https://raw.githubusercontent.com/shadps4-emu/shadPS4/main/src/core/libraries/kernel/memory.h). [PS4/Emu]

Gap to note: SharpEmu uses `DefaultDirectMemoryBytes = 13824 MiB` (KYTY's `PhysicalMemory::TotalSize()` at `src/kernel/memory.cpp:667`, an assumption). The only real-hardware number found is about 12,288 MiB at a 448 MiB flexible size. SharpEmu `src/SharpEmu.Libs/Kernel/KernelMemoryCompatExports.Budget.cs:13-14`. Titles that size their pools from the reported value are given about 1.5 GiB more than the real console gives them.

**Budget decision (resolved the gap above).** SharpEmu now reports `direct = 12,736 MiB title total - flexible`, so 12,288 MiB (`0x3_0000_0000`) at the 448 MiB default and 12,416 MiB at 320 MiB, matching the ProsperoEden #156 measurement and the direct + flexible invariant (not a fixed 12 GiB). Flexible still comes from `param.json` (default 448 MiB). Demon's Souls' page allocator takes everything `sceKernelGetDirectMemorySize` reports and treats anything above its retail constant `0x3_0000_0000` as "debug memory" (`artifacts/phase1/guest-memory.md`), so the old 13,824 MiB gave it about 1.5 GiB that a console never would. `SHARPEMU_DIRECT_MEMORY_MB` overrides the direct size outright. Code: `KernelMemoryCompatExports.Budget.cs`, tests: `KernelMemoryBudgetTests`. Caveat: the 12,288 MiB figure is from a homebrew process on firmware 6.02; a retail title may see a slightly different value.

### 2. Direct memory

API surface (all in SDK `sys/dmem.h`):

- `sceKernelAllocateDirectMemory(searchStart, searchEnd, len, alignment, memoryType, &physOut)` reserves a physical extent. It returns a **physical offset**, not an address, and does not map anything. `...2` adds a flags argument. `sceKernelAllocateMainDirectMemory(len, alignment, type, &out)` searches the whole main range. `sceKernelReleaseDirectMemory` / `CheckedRelease...` free it.
- `sceKernelMapDirectMemory(&addr, len, prot, flags, physStart, alignment)` maps a previously allocated extent into the virtual address space. `...2` adds a type, `sceKernelMapNamedDirectMemory(..., name)` labels the mapping (name up to 32 bytes, shown in `sceKernelVirtualQuery`).
- `sceKernelBatchMap[2]` performs `MAP_DIRECT`, `UNMAP`, `PROTECT`, `MAP_FLEXIBLE` and `TYPE_PROTECT` in one call. Entries run in order, and the call returns the number completed.
- `sceKernelMtypeprotect`, `sceKernelDirectMemoryQuery`, `sceKernelGetDirectMemoryType`, `sceKernelVirtualQuery` expose type, protection and the `isDirectMemory / isFlexibleMemory / isPooledMemory / isCommitted / isGpuPrt / ammUsage / isStack` bits.
- The kernel entry points are `sys_mmap_dmem` (0x274), `sys_mtypeprotect` (0x17b), `sys_virtual_query` (0x23c), `sys_dmem_container` (0x24a). SYSCALLS lines 316, 478, 483, 525.

Semantics:

- **Allocate and map are separate.** Alignment is a power of two. Sony code uses 16 KiB (the minimum, `SAMPLES: graphics/tutorial_asset_streaming/sample/include/utils.h` `0x4000`), 64 KiB, 1 MiB (`api_apr/main.cpp:52`) and 2 MiB (`tutorial_cpu_parallel_processing/helper/direct_memory.cpp`, `kDmemAlign`). AMM-managed memory must be a multiple of **2 MiB** in size and alignment (`SDK: ampr/amm.h`, `giveDirectMemory`).
- **Memory types.** PS5 SDK 10.00 exposes only `SCE_KERNEL_MTYPE_C = 11` and `SCE_KERNEL_MTYPE_C_SHARED = 12` (end marker 21). `SDK: sys/dmem.h`.
  - `C_SHARED`: CPU writes invalidate valid GL2 lines, so the GPU re-reads fresh data. Sony samples use it for nearly every CPU+GPU buffer (`SAMPLES: tutorial_graphics_programming/01-hello_triangle/hello_triangle.cpp:37`).
  - `C`: CPU writes do **not** invalidate GL2; the title must invalidate. Neither type helps if the GL2 holds a *dirty* line the CPU then overwrites; the line is later written back over the CPU's value, which is "practically always a bug". `SDK: agc/commandbuffer.h:403-427`.
  - There is no PS5 "WC/Onion/Garlic" choice in this header. The PS4 types were `WB_ONION = 0`, `WC_GARLIC = 3`, `WB_GARLIC = 10` (shadPS4 `libraries/kernel/memory.h`, [PS4/Emu]). `mman.h` still has `MAP_WRITABLE_WB_GARLIC = 0x00800000`. Titles built for PS4 and run on PS5 map those values onto the two PS5 types (inference, no source).
  - `sceKernelMtypeprotect` and AMM `modifyMtypeProtect` change type and protection of an existing mapping. The AMM `multiMap` alias gets its own protection but keeps the memory type. `SDK: ampr/amm_command_buffer.h:261-289`.
- **Protection bits.** CPU `READ=0x1, RW=0x2, EXEC=0x4`; GPU `READ=0x10, WRITE=0x20`; AMPR (APR/AMM engines) `0x40/0x80`; ACP `0x100/0x200`. The GPU bits are real page-table permissions the GPU enforces. `SDK: sys/dmem.h`. Some protections cannot be removed because of hardware limits; CPU, AMPR and ACP do not support write-only (`amm_command_buffer.h:368,471`). Homebrew reports `mmap(RWX)` yields RW only and `mprotect(EXEC)` fails, with JIT going through `sceKernelJit*` shared-memory aliases (https://github.com/ZigZagBoi1/PS5-14.10-Research, community; `SDK: sys/dmem.h` JIT API).
- **Map flags.** `FIXED 0x10`, `NO_OVERWRITE 0x80`, `DMEM_COMPAT 0x400`, `NO_COALESCE 0x400000`, `ALIGNED(n) = n << 24` with the alignment in log2 (14 = 16 KiB, 16 = 64 KiB, 21 = 2 MiB, max 31). `SDK: sys/dmem.h`.
- **Page sizes.** `SCE_KERNEL_PAGE_SIZE = 16384`. Every map/unmap/query length and address is a multiple of 16 KiB (AMM and APR headers repeat "must be a multiple of SCE_KERNEL_PAGE_SIZE"). A 14.10 research dump reports `sysctl` page size 16 KB and contiguous 16 KB GPU-mmap pages (https://github.com/ZigZagBoi1/PS5-14.10-Research). So the title-visible granule is **16 KiB, the same as Apple Silicon**. GPU-side granules are larger: 64 KiB tiled-surface alignment (`Alignment::kMaxTiledAlignment = 65536`, `SDK: agc/baselayer.h:71`; `kStandard64KB`) and 2 MiB page-table-pool entries (see section 3). Whether the CPU PTEs underneath use 4 KiB is [Unknown] and not visible to the title.
- **Page contents on allocate/map.** [Unknown] for the real kernel. No SDK text promises zeroed dmem. FreeBSD zero-fills anonymous pages on first touch (`FBSD: vm_fault.c:1030-1031`, `pmap_zero_page`), and the flexible/anon side of the PS5 kernel is FreeBSD-derived, so first-touch zero for flexible memory is a safe assumption. shadPS4 does not zero on allocate/map/pool-expand and only zeroes on flexible unmap (`src/core/memory.cpp`, [Emu]); KYTY zeroes backing blocks when mapping flexible memory (`src/kernel/memory.cpp:1737`, [Emu]). Titles that depend on dmem being zero are rare; zero on first touch is the least surprising behaviour.
- **GPU-visible alias rules.** `isGpuPrt`, `gpuMaskId` and `ammUsage` are per-range attributes in the page tables. `mapWithGpuMaskId` and friends set `gpuMaskId` (default 0). `SDK: ampr/amm_command_buffer.h:80-107`.

### 3. Flexible memory, libc heap, pools, PRT, address layout

**Flexible memory** (`sceKernelMapFlexibleMemory`, `...NamedFlexibleMemory`, `sceKernelReleaseFlexibleMemory`, `SDK: sys/dmem.h`):

- A budgeted, anonymous, kernel-chosen-physical mapping. The budget is the 448 MiB default or `kernel.flexibleMemorySize`. It is CPU-only by default; GPU bits may be added (`SCE_KERNEL_PROT_GPU_*` are accepted by `BatchMap` `MAP_FLEXIBLE`).
- Not necessarily physically contiguous (contrast with direct allocations).
- `sys_get_resident_fmem_count` (0x267) and `sys_set_phys_fmem_limit` (0x27d) show the kernel tracks *resident* flexible pages separately from mapped ones. SYSCALLS lines 512, 534. Mapped is charged to the budget immediately; residency is on demand (FreeBSD `vm_fault`, `FBSD: vm_fault.c:782,1030`). [FBSD + inference]
- Image segments (executable and libraries) are charged to flexible memory: a title's modules plus tracked mappings exceeded 448 MiB in the Black Myth case (about 538.8 MiB), which is why it declares 800 MiB. https://github.com/boykopovar/AnyPS5/pull/4508 [community]

**libc heap** (`SDK: stdlib.h:439-453`): titles configure the system `malloc` with exported globals `sceLibcHeapSize`, `sceLibcHeapInitialSize`, `sceLibcHeapExtendedAlloc`, `sceLibcHeapDelayedAlloc`, `sceLibcHeapHighAddressAlloc`, `sceLibcHeapMemoryLock`, `sceLibcHeapDebugFlags`; `SCE_LIBC_HEAP_SIZE_EXTENDED_ALLOC_NO_LIMIT = ~0`. `mspace.h` gives private heaps (`sceLibcMspaceCreate(name, base, capacity, flag)`). The header does not document the flags. The names are explicit enough to read as: initial vs maximum heap size, grow-on-demand ("extended alloc"), commit-late ("delayed alloc"), and place-in-high-VA. That reading is [Unknown]-grade inference. The libc heap is built on top of `sceKernelMapFlexibleMemory` / direct memory, so it shows up as flexible and direct mappings, not as a separate kernel concept.

**Memory pools** (blockpool). Syscalls `sys_blockpool_open/map/unmap/batch/move` (0x28d, 0x28e, 0x28f, 0x291, 0x2a1; SYSCALLS lines 550-554, 570) back the libkernel API in `SDK: sys/dmem.h`:

- `sceKernelMemoryPoolExpand(searchStart, searchEnd, len, alignment, &phys)` adds physical blocks to the process pool (charged to the pool budget).
- `sceKernelMemoryPoolReserve(addrIn, len, alignment, flags, &addrOut)` reserves virtual range only (no physical).
- `sceKernelMemoryPoolCommit(addr, len, type, prot, flags)` assigns pool blocks to the reserved range with a type and protection; `Decommit` returns the blocks to the pool and the VA goes back to reserved (no access); `Move` relocates committed blocks; `Batch` runs `COMMIT/DECOMMIT/PROTECT/TYPE_PROTECT/MOVE` entries.
- `sceKernelMemoryPoolGetBlockStats` returns `{availableFlushedBlocks, availableCachedBlocks, allocatedFlushedBlocks, allocatedCachedBlocks}`, so blocks come in "flushed" and "cached" flavours (presumably matching the two memory types).
- Block granularity is 64 KiB in shadPS4 (`PoolExpand`/`PoolCommit` use `64_KB`); commits can map sparse physical pieces ("On PS4, commits can make sparse physical mappings"), the budget check is strict, and `isPooledMemory` / `isCommitted` are reported by `VirtualQuery`. https://raw.githubusercontent.com/shadps4-emu/shadPS4/main/src/core/memory.cpp [Emu]. The API shape is [SDK]; the granularity and strictness are [Emu].
- Typical use: engines reserve a large VA window once, then commit/decommit blocks as streaming proceeds, instead of mapping/unmapping direct memory. Footprint tracks *committed* blocks, not the reserved window. [Inference from the API; no title-specific source.]

**PRT (partially resident textures)**:

- `sceKernelSetPrtAperture(index, addr, len)` / `GetPrtAperture`, at most 3 apertures (`SCE_KERNEL_MAX_PRT_APERTURE_INDEX = 2`). A **fixed** PRT aperture exists at `0x0f_0000_0000`, size `0x1000_0000` (256 MiB). `SDK: sys/dmem.h`. KYTY accepts aperture ranges between `0x0f_0000_0000` and `0xfc_0000_0000` in 16 KiB units (`src/kernel/memory.cpp:921-923,2401`) [Emu].
- PRT memory "does not have associated PA": a CPU access faults, and its type, protection and GPU mask cannot be changed. `mapAsPrt` creates it; `allocatePaForPrt` gives it PA and clears the PRT flag; `remapIntoPrt` moves an existing mapped range into a PRT hole and removes the old mapping. `SDK: ampr/amm_command_buffer.h:529-620`.
- GPU side: `TileMode::kStandard4KB` "can be used for PRT"; `kPrt` is a PRT-specific layout that cannot be compressed. Depth/stencil surfaces have `PartiallyResidentDepth/Stencil` bits. `SDK: agc/registerstructs.h:19947-19958, 16229-16300`.
- shadPS4 serves reads of unbacked PRT pages as zeros (`CopySparseMemory`, `memset 0`, 16 KiB steps; the zero-read behaviour is the usual PRT contract but no Sony header states it) [Emu]. Sony's texture-streaming sample stages mip data at 64 KiB boundaries ("Align up the top to 64k boundary") and uses AMM `map`/`unmap`/`remap`/`multimap` commands (`SAMPLES: graphics/tutorial_texture_streaming/common/texture_streaming.cpp:207-240,654-690,1055`) [SDK].
- Partial mapping cost: for each 2 MiB of VA that is partially mapped by AMM, exactly one page-table-pool entry is consumed (`SDK: ampr/amm.h:74-78`). A fully mapped 2 MiB region does not take one.

**Virtual address layout** (`SDK: sys/dmem.h`, SPEC 0.2):

- App map area: `0x10_0000_0000 ... 0xfc_0000_0000` (944 GiB), the range that `sceKernelMapDirectMemory`, flexible and pool mappings land in.
- Fixed PRT aperture at `0x0f_0000_0000` below it. Everything is below 1 TiB (40-bit; the GPU "can only handle 40 bit addresses", shadPS4 `memory.h` comment [PS4/Emu]).
- Default placement when the title passes no address: KYTY searches from `0x2_0000_0000` (`src/kernel/memory.cpp:2252,2321`) and shadPS4 `DEFAULT_MAPPING_BASE = 0x200000000` [Emu]. Homebrew notes that unconstrained CPU mappings can land in a window the GPU driver needs later, so loaders pin buffers at fixed addresses such as `0x10_0000_0000` (PS5LM RESEARCH.md, [community]).
- AMM has its own managed VA range and a tail "multimap" range, queried by `Amm::getVirtualAddressRanges` (`SDK: ampr/amm.h:43-61`).
- System-reserved and loader regions are not given in any header (shadPS4 asks `AddressSpace` for `SystemReservedVirtualBase`). [Unknown]

### 4. How the GPU accesses memory

- One address space and one pool: the GPU reads and writes the same GDDR6 pages the CPU maps. There is no upload step or VRAM copy; a "buffer" is a pointer plus a descriptor. All Sony samples allocate one direct block, map it `CPU_RW | GPU_RW`, then fill it from the CPU (`SAMPLES: tutorial_graphics_programming/01-hello_triangle/hello_triangle.cpp:37-45`).
- **Tiled surfaces live in place.** Tile modes (`SDK: agc/registerstructs.h:19947`): `kLinear`, `kStandard256B`, `kStandard4KB`, `kStandard64KB`, `kPrt`, `kDepth`, `kRenderTarget`. The CPU sees the raw swizzled bytes; the title (or its toolkit) detiles through shaders or tiling helpers when it needs to. Maximum alignment for tiled memory is 64 KiB. `SDK: agc/baselayer.h:71`.
- **Caches and coherence.** The GPU has a GL2 cache; `kLru`, `kStream`, `kNoalloc`, `kBypass` policies; ranged or full `kGl2Writeback` and `kGl2WritebackInvalidate` packets (`acquireMem`, `queueEndOfPipeAction`). The CPU cannot trigger a writeback itself. `SDK: agc/commandbuffer.h:65-125, 403-480`. Metadata (CMASK, DCC, HTILE) lives in ordinary memory beside the surface (`MetadataPipeAlignment`).
- **"GPU-only memory"** is not a separate physical pool. In this model it is memory mapped with GPU protection bits and no CPU bits (or PRT with no PA at all). The deprecated `GPU_PRIVATE_DMEM` region (2 GiB) was the PS4-era version. `SDK: sys/dmem.h`. A GPU-only mapping still costs GDDR6, and the CPU page tables just do not point at it. [SDK for the bits; "no separate pool" is inference.]
- Dirty-line hazard: CPU writes to a line the GPU has dirty in GL2 lose to the eventual GL2 write-back. Emulating this exactly is not required, but an emulator that does CPU/GPU sharing with no copies must still make GPU writes visible before the CPU reads them. `SDK: agc/commandbuffer.h:403-427`.

### 5. File-backed memory, APR, AMPR, and streaming

- **AMPR** is the family of asynchronous memory engines: **APR** (async page/file read) and **AMM** (async memory mapping). Titles build command buffers in memory mapped with `SCE_KERNEL_PROT_AMPR_RW` (up to 64 MiB, `SCE_AMPR_COMMAND_BUFFER_SIZE_MAX`), submit them, and wait on labels or on `EVFILT_AMPR` events. `SDK: ampr/*.h`; `SAMPLES: system/api_apr/main.cpp`. Syscalls: `sys_apr_submit/resolve/stat/wait/ctrl` (0x2bc-0x2c0) and `sys_ampr_ctrl_debug` (0x2d1), SYSCALLS lines 593-614.
- **APR read model.** Files are first resolved from absolute path to an `APRFileID` (`resolveFilepathsToIds`; the path must be in a PlayGo chunk definition). `readFile(id, buffer, length, offset)` reads up to 4 GiB at offsets below 1 TiB into memory mapped with `AMPR_WRITE`. Gather/scatter variants exist. `SDK: ampr/apr_command_buffer.h:85-118`, `apr.h:88-110`. The read is a DMA into the mapped memory with no CPU copy. The headers say nothing about Kraken; the `ampr` headers do not mention decompression (`grep` for kraken/oodle/zlib across the SDK headers only hits `libpfs.h`). Sony's public statements say the I/O complex has fixed-function Kraken (and zlib) decompression, a DMA controller, two I/O co-processors, SRAM, coherency engines and cache scrubbers, 6 priority levels, with at least 5.5 GB/s raw and 8-9 GB/s typical (secondary coverage of "Road to PS5": https://www.digitallydownloaded.net/?p=42156, https://twinfinite.net/2020/03/ps5-technical-reveal/). [Real HW spec, secondary source]
- **mapBegin / mapEnd.** An APR sequence may map pages (`mapBegin` = AMM `map` of AUTO memory; `mapDirectBegin` = map direct memory), read files into them, then `mapEnd`. Reads that overlap the mapped range are faster "because GPU cache rinse work is disabled in the overlapped region", and no write-on-completion commands are allowed inside the pair. `SDK: ampr/apr_command_buffer.h:268-292, 404-420`. This shows the intended flow: **allocate, map and fill happen in the I/O engine, directly into final memory**, and the GPU's caches are rinsed around it.
- **AMM** commands: `map` (AUTO memory), `mapDirect`, `unmap` (partial unmap of a large mapping is allowed), `remap`, `multiMap` (alias), `modifyProtect`, `modifyMtypeProtect`, `mapAsPrt`, `allocatePaForPrt`, `remapIntoPrt`, each with a `...WithGpuMaskId` form. AUTO memory comes from `Amm::giveDirectMemory(..., Usage::kAuto, &off)`, which hands **2 MiB-aligned, 2 MiB-multiple** direct memory to AMM; the pages AMM picks "are not guaranteed to be physically contiguous". `SDK: ampr/amm.h:165-210`, `amm_command_buffer.h:52-134`. `AmmUsageStats` reports `snapshotFree2MiBPaSegmentCount`, i.e. free 2 MiB PA segments.
- **Texture/asset streaming in practice** (Sony samples): a streaming heap is one large `AllocateDirectMemory` (`MTYPE_C_SHARED`, 64 KiB or larger allocation unit) mapped `CPU_RW | GPU_RW | AMPR_RW`, named `"sce.AssetStreamer"`; textures are made resident by AMM map commands in 64 KiB granules as mips stream in. `SAMPLES: tutorial_asset_streaming/lib/source/core_streamer.cpp:238-246`, `tutorial_texture_streaming/common/texture_streaming.cpp:3330-3333`.
- Non-AMPR file I/O uses FreeBSD `mmap` of files, AIO syscalls (`sys_aio_*`), and `sys_apr_*`/`fsc2h_ctrl` streaming reads (SPEC section 5.5). File-backed mappings drop the execute bit silently on real hardware (shadPS4 `MapFile` comment, [Emu]).

### 6. Implications for SharpEmu on Apple Silicon (derived; not facts)

These follow from the facts above plus Darwin behaviour. They are proposals to evaluate, not findings.

1. **The 4 KiB vs 16 KiB concern in GOAL.md is smaller than assumed.** The title-visible granule is 16 KiB (`SCE_KERNEL_PAGE_SIZE`), the same as Apple Silicon's page. Every map/unmap/protect/query is 16 KiB-granular, so a host mapping of exactly the guest's ranges wastes nothing. Waste comes only from SharpEmu's own sub-16K bookkeeping or from rounding windows up past what the guest asked for. Direct-memory sub-ranges at 64 KiB / 2 MiB alignment are an *address alignment* demand, not a granule.
2. **Budget the right numbers.** Real hardware reports roughly 12,288 MiB direct plus 448 MiB flexible (or the title's declared flexible size, with direct shrinking correspondingly). SharpEmu reports 13,824 MiB direct. Titles that size pools from `sceKernelGetDirectMemorySize` or `AvailableDirectMemorySize` will request up to 1.5 GiB more than on the console. Set the budget to the measured value, and keep `direct + flexible` constant when `param.json` changes flexible.
3. **Reserve virtual, commit physical lazily.** Direct allocation (physical extent), flexible map, pool reserve and PRT map are all "claims" on the real console; only touched pages occupy GDDR6 (FreeBSD faults pages in, `FBSD: vm_fault.c`). Map the backing as `MAP_ANON`/memory-entry pages that are never touched until the guest touches them, so a 12-14 GiB budget costs nothing until used. Do not `memset`, pre-fault or `mlock` at allocate/map time, and do not zero at allocate (real dmem zeroing is unspecified; fresh anon pages are already zero).
4. **Give memory back where the real kernel does.** On `sceKernelReleaseDirectMemory`, `ReleaseFlexibleMemory`, `MemoryPoolDecommit` and unmap, the physical pages are free for reuse. Use `madvise` to drop them. Darwin provides `MADV_FREE` (lazy, RSS stays until pressure), `MADV_FREE_REUSABLE`/`MADV_FREE_REUSE` (Darwin-specific; designed so freed pages stop counting toward the process footprint, to be verified with `footprint`) and `MADV_ZERO` (zero without faulting in) (`~/Documents/ps5emu/docs/macos/mman.h:215-224`). `MADV_FREE_REUSABLE` then `MADV_FREE_REUSE` is the closest fit for decommit followed by re-commit. For re-committed memory a title may expect zero (flexible/anon): `MADV_ZERO` or remap fresh pages.
5. **Pools: footprint should track committed blocks.** Back `MemoryPoolReserve` with `PROT_NONE` virtual space only, and make `Commit` populate 64 KiB blocks on demand; `Decommit` returns them (point 4). Do not reserve the pool at full size as committed memory.
6. **Share guest memory with Metal instead of mirroring it.** The console model is "one pool, no copies, tiled data in place". Apple Silicon is also unified, so a GPU-visible guest range can be wrapped with `MTLDevice.makeBuffer(bytesNoCopy:)` (needs page-aligned, 16 KiB-multiple length: matches the guest granule) rather than copied into a second buffer. Textures need a swizzle/detile step because the guest bytes are in AMD tiled layouts (64 KiB `kStandard64KB`, 256 B/4 KiB variants), so a texture is a derived *view* of the buffer, and any detiled copy is a cache that must be bounded and evictable. The SPEC.md plan (section 7.2) already says this: residency keyed by physical byte range, three-valued dirty tracking, no destroyed unpublished GPU writes.
   *Implemented (Metal V2 image cache):* the detiled copies are sized against the host, not a share of RAM: budget = clamp(min(physical - (process footprint - cache) - headroom, cache + available - reserve), floor, ceiling), where available is free + pageable file-backed pages (XNU memorystatus' own measure) and the guest's resident memory is inside the process footprint; WARN pressure halves it, CRITICAL drops it to the floor. Images idle for 600 frames and 20 s are released regardless of budget (GPU-written ones are written back first). Code: `MetalImageBudget.cs`, `MetalHostMemory.cs`, `MetalImageCache.Budget.cs`; tests: `MetalImageBudgetTests`.
7. **Honour GPU/CPU coherence only as far as needed.** On real hardware CPU writes to `MTYPE_C_SHARED` memory invalidate GL2 and CPU reads after a GPU write need a writeback first. On unified Apple memory with `storageModeShared` buffers no cache maintenance is needed beyond command-buffer completion; a `GL2 writeback` packet can map to "make GPU writes visible" (fence/wait) and `kGl2Writeback|Range` to a range-limited flush of tracked dirty regions.
8. **PRT and AMM partial maps are sparse by definition.** Treat `mapAsPrt` ranges as address space with no backing, treat `allocatePaForPrt`/`remapIntoPrt` as commit points, and unmap with partial ranges. Apple GPUs have sparse textures (`MTLHeap` sparse mode, 16 KiB tiles on M-series via `MTLSparsePageSize`), a natural fit when a PRT-tiled surface's backing is the PRT resource. Do not allocate full-size backing for a PRT aperture.
9. **Stream directly into final memory.** An APR `readFile` writes into the destination with no intermediate copy. SharpEmu should read (and decompress) into the guest mapping, not into a managed buffer that is copied over. Large staging arrays on the .NET LOH are avoidable. Where decompression is needed it should run into the destination range (`pread` into the mapped pages, then in-place Kraken). Reads bigger than a few MiB should not be pinned managed arrays.
10. **Page-table pools are a budget, not memory.** `sceKernelGetPageTableStats` and the AMM page-table-pool counters report entries (2 MiB of VA per partially mapped region), not bytes of RAM. Report consistent small numbers and do not allocate host memory for them.
11. **Executables are charged to flexible memory on the console** (about 538 MiB of image + mappings in one title against a 448 MiB default). If SharpEmu loads images into the same budget as guest flexible memory, loaded modules and their relocation copies count against the flexible limit and a title may legitimately declare a larger size. Do not give the loader its own extra copy of module data.
