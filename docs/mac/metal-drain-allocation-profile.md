# Presenter drain allocation capture

`SHARPEMU_PROFILE_ALLOCATIONS=1` opts into a separate bounded allocation trace. The flag is cached at process startup. It can run alone, or with the existing wall profile (`SHARPEMU_PROFILE_PERFORMANCE=1` / `SHARPEMU_PROFILE_RENDER=1`). Allocation-only mode does not enable the wall profiler's clocks. The existing drain's execution-budget clock is unchanged. With allocation capture off, no new allocation-counter, thread-ID, storage or clock reads occur in its measurement path; completion instrumentation checks only the cached flag.

The counter is `GC.GetAllocatedBytesForCurrentThread`, sampled immediately before and after the actual main-presenter `DrainGuestWork` invocation, including preparation, execution, acknowledgement and its final flush. Nested drains share the outer delta, while retaining their call/failure counts. Counter setup and export happen outside the measured delta. Allocations on command-stream, decoder, CPU guest and other threads are excluded. This measures allocated managed bytes, not live heap size, native texture/upload bytes, GC pauses, CPU self-time or GPU time. It does not remove allocations or prove an optimization.

Completed-work counters increment only after `CompleteGuestWork` returns successfully. Draw and compute counters classify those acknowledged objects. Existing intentional skipped/no-op paths still count as acknowledged draw/compute work; these counters are not actual GPU dispatch or render-encoder counts. Failed work remains unacknowledged, preceding successful work is retained, and failed/partial drains remain visible. Byte totals include failed-item allocations and drain housekeeping; dividing by acknowledged work is an aggregate ratio, not allocation attribution to each work item.

Host redraw drains accumulate in pending counters without creating rows. The existing unique guest-frame command-buffer commit boundary stores one allocation row with the same trace ordinal as the wall profile (when enabled), and the actual guest frame sequence. This is neither GPU completion nor display scanout. The separate `METAL_DRAIN_ALLOC_TRACE`, `METAL_DRAIN_ALLOC_FRAME` and `METAL_DRAIN_ALLOC_TAIL` prefixes leave all previous `METAL_PRESENT_*` fields unchanged. Rows retain the latest 4,096 guest commits with explicit overwritten count. Profile End exports work after the last commit in the tail, including managed fatal work when no guest row was produced. Native/process termination before End can omit the report; absence remains unknown.

Measurement belongs to the presenter thread identified at profile `Begin`. A scope started or finished on another thread is explicitly discarded. Stale/out-of-order scopes are also discarded, with an epoch preventing a late scope from reading a new scope's counter. Any `discarded_scopes>0` makes coverage partial; missing values must not become zero. Scope misuse may omit bytes and is reported as unknown coverage, not a successful measurement. Rejected foreign-thread scopes use an atomic discard counter; each guest row atomically consumes it, so concurrent rejected scopes cannot be lost by copying and clearing the owner counters. Rejected scopes do not invalidate an active owner measurement. An accepted scope finished on the wrong thread does invalidate that measurement. `Begin` and `End` are quiescent presenter-session/reset/export boundaries, not concurrent multi-thread session operations. `Begin` deliberately clears previous-session data; callers still running across a reset or after export are outside the captured window. `End` reads the tail discard counter atomically without consuming it, preserving counters if diagnostic output fails. A new session clears rows, pending state and thread identity. Native window/overlay cleanup still precedes export, and existing ordinary closed-output failure suppression is preserved.

Decode a completed single-session log with:

```sh
python3 tools/profile/metal_drain_allocations.py game.log --output allocations.json
```

The decoder retains original wall fields and correlates by trace ordinal. Legacy timing-only logs report allocation data as uncollected. Allocation-only rows report wall fields as absent. Truncated/duplicate reports, invalid schema/scope, bad counters and noncontiguous retained windows fail explicitly; split concatenated sessions first. The new stream has schema1; the legacy wall stream is not versioned or changed by this patch.

Source controls exercise real managed queue draining/acknowledgement, a deliberate managed allocation, partial fatal work with the original cause and following work unacknowledged, and legitimate skipped draw/compute completion without Metal calls. Additional controls cover nested byte deduplication, unrelated-thread exclusion, wrong-thread/stale-scope discard, exact concurrent rejected-scope counts across commits/tail without owner-byte cancellation, bounded ring/reset, allocation-only output and default-off warmed zero allocation. Enabled facts declare a skip unless a fresh process has the allocation flag; disabled facts declare a skip if allocation/wall profiles are enabled. Run the enabled and disabled selections separately and report actual execution counts. No hardware, game or performance measurement is qualified by these tests.

Managed qualification on native ARM64 and Rosetta/x64 passed, in separate fresh processes per flag set: allocation enabled 8/8, disabled 1/1, legacy drain/fatal/readiness/scheduling 43/43, and allocation plus wall profile 2/2 on each CLR, with no skips. The concurrent control retains all 1,048,576 rejected scopes across 256 commits plus tail; every owner row retains its controlled allocation. The warmed disabled control measures zero allocated bytes across 10,000 scope/completion/commit calls. The final incremental build has 104 existing warnings and zero errors (the initial full build had 154 warnings and zero errors). The offline decoder passes 9/9 controls; eight actual success/fatal/no-op/mixed reports extracted from the final TRX decode and preserve the asserted counters and wall correlation.

These are controlled instrumentation checks, not a native/game allocation profile or optimization. The selected fixtures contain no platform early-return gate; the enabled/disabled Fact attributes deliberately declare skips under the wrong process flags, so use the recorded separate selections. The legacy managed controls and normal test-process host startup remain unchanged. No GPU, game, native fault/protection fixture or runtime performance result is qualified by this patch. Live captures are still needed before choosing any hot allocation rewrite.
