# HLE wall-time attribution and loading audit

The Quake native baseline at `artifacts/runs/20261008-034019-quake-all-games-baseline-8c19cd7/game.log` records video handle `0x1C05A9000` at clock 1000 and 11000 ms. Deltas are 1,126,233 polls, 240 delivered frames, zero decoder-pending returns and 1,125,993 sync-wait returns: 112,623.3 polls/second, 24 delivered frames/second, 99.97869% sync-wait. This is a ten-second media-clock window of an encoded intro, not gameplay FPS or CPU time. The title later rejects a requested 256 MiB texture payload against the separate 128 MiB snapshot cap.

`GetVideoData` takes the shared player state gate, reads the playback clock and checks its existing decoder; the sync-wait branch returns before frame copying, image conversion and per-frame string tracing. Existing video statistics format output once per second. High call counts alone cannot rank its CPU cost. Adding sleeps/yields to the guest nonblocking API, changing audio-master time or accelerating an encoded intro would change semantics.

## Isolated opt-in timing correction

`SHARPEMU_PERF_HLE=1` previously held only the last export name in thread-local state. A nested callback import overwrote the parent's name, and both parent and child inclusive times were summed under a misleading `cores` label. The corrected enabled gateway uses a balanced bounded per-thread frame stack, retaining the outer export name and subtracting only nested gateway elapsed intervals. Finally completion includes managed exceptions. Ordinary closed profiling sinks cannot skip the export or replace its result/error.

Inclusive wall time includes nested import work. Exclusive wall time excludes those nested gateway intervals; it still includes guest callback execution outside a nested gateway, waits, renderer work and scheduler activity. Neither metric is host-thread CPU self time. No CPU-core estimate is printed. Separate process/thread CPU sampling is required to distinguish waiting from execution.

Counters are process-cumulative, initialized at process/type startup, and do not reset at an arbitrary game session or frame. Compare deltas from the same PID/source/clock and export; snapshots taken while workers run are approximate moving observations rather than atomic exact frame boundaries. A new process is the supported reset boundary. Reports every 500,000 recorded completed scopes avoid repeated reports caused by another thread observing a started-call milestone. Counters retain current begun/ended distinctions. Above 128 nested recorded gateway frames, scopes are explicitly omitted and counted separately; they do not enter the `recorded_completed` denominator or the inclusive average. Parent exclusive time still subtracts the first omitted child's full elapsed interval. Such a report is incomplete and cannot serve as complete attribution acceptance.

The disabled gateway retains its original path: no timing stack access, additional timestamps, allocation or profiling synchronization. Enabled mode allocates one bounded frame array per profiled managed thread, then reuses value-type scopes without per-call frame allocation. This is ordinary managed import code, not a signal callback warm-up or native fault-safety claim. Profiler overhead is part of measured elapsed time; final FPS/load acceptance needs an uninstrumented run.

## Lessons checked against local projects

- `kairo/scripts/analyze_cpu_work.py` compares exact matching frame rows, rejects missing boundaries, changed clock policy and counter resets, and separates thread CPU from stage wall time. Adopt those checks for future SharpEmu exact-frame CSV rather than treating reset/windowed counters as monotonic.
- `kairo/crates/kairo-emu/src/run/work_profile.rs` explicitly tracks inclusive versus exclusive nested stage time and separately samples the emulator thread CPU clock. The new HLE correction follows that nested accounting principle but does not import its interpreter or guest clock policy.
- `REmu/crates/remu-runtime/src/av_player.rs` has background bounded decoder queues and a nonblocking `poll`/clock-not-reached return. Its decoder-thread retry sleeps are not guest API sleeps. Its explicit clock and source-drain state checks are useful acceptance fixtures, not permission to transplant REmu's catch-up policy into SharpEmu.
- `kairo/crates/kairo-emu/src/av_player.rs` keeps pending video frames until their media timestamp is due. Preserve timestamps, audio master, pause/seek and EOF behavior when measuring SharpEmu delivery, rather than imposing a global 60 FPS media clock.

## Next measurements and package choices

Collect exact intro/loading/gameplay windows separately: per-export wall costs, native thread CPU samples, CLR allocation/GC/lock contention, shader/pipeline compilation and guest frame/submission gaps. [Microsoft's CPU diagnostic guide](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/debug-highcpu) pairs runtime counters with sampled traces; [dotnet-counters](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/dotnet-counters) and [dotnet-trace instructions](https://github.com/dotnet/diagnostics/blob/main/documentation/dotnet-trace-instructions.md) provide primary tool contracts. Managed samples will not fully account for direct guest x64 execution or native Metal compiler/device work; correlate with native sampling and exact guest events. No profiler has been attached to these baseline games by this change.

The existing platform packages already select native audio/Metal/fonts/AppKit and exclude portable Mac frontend dependencies. Keep settings/catalogue/launch contracts neutral; a .NET runtime diagnostics adapter or tooling script can remain optional instead of adding UI dependencies to Core. Do not swap FFmpeg, queue packages, logging packages or enable NativeAOT on the strength of poll counts. First measure background decode startup, StateGate contention, catalog rescans/JSON/cover loading, assembly/JIT warm-up and guest copying allocations. `System.Threading.Channels` is a candidate only if measured queue contention or ownership complexity justifies replacement; it must preserve bounded memory, nonblocking polling and owned-buffer disposal. No package substitution or global GC/JIT knob is enabled by this audit.


## Isolated validation scope

The focused selection passes 10/10 on native ARM64 and 10/10 on Rosetta x64 with profiling off, and 9/9 on each with `SHARPEMU_PERF_HLE=1`. Enabled runs explicitly exclude the disabled-branch assertion; no fixture uses a platform early return. Controls use the actual managed gateway and its enabled helper with fixture-managed exports and a zeroed argument packet; they do not execute native guest instructions, install fault callbacks or qualify guest callback ABI. The fixture intentionally uses a trivial import classification to avoid unrelated backend/native setup while exercising recursive gateway calls.

Synthetic timestamps check exact child subtraction and bounded overflow through the actual reporter: 130 nested scopes produce 128 recorded completions and two separately omitted scopes, with 256 exclusive ticks. Warmed timing scopes allocate zero bytes across 10,000 begin/name/complete operations; this does not claim the entire export/gateway or first per-thread initialization is allocation-free. Real gateway success/error returns and name counters are checked in both modes. Actual enabled helper report writes are forced to an ordinary I/O failure; original export exception/result is retained. No game, UI, GPU, native guest execution or profiler attachment is part of this validation.

Separate Release test build has zero errors and existing unrelated warnings (124 in the initial and recorded-denominator successor builds, 107 in the original final incremental build); no warning names the new timing source/tests. Isolated CLI Windows and Linux cross-builds each have zero errors and four existing warnings in their respective incremental builds. Cross-OS runtime behavior is unexecuted. No FPS, faster loading or CPU reduction is claimed by this diagnostic correctness change.
