# Shared backing lifetime increment

Bounded ordinary backing design with managed and separately granted actual Mac provider controls. No POSIX recovery callback, tracker retry, native page permission, or registry activation.

The backing object owns the CPU alias mapping and storage descriptor. It does not own every guest virtual view, and kernel views can survive descriptor close. A pin retains the alias/descriptor against explicit backing disposal only; it does not authorize guest writes, serialize content writes, or establish virtual mapping identity.

macOS creates immutable backing identity, logical backing size, native page size, and rounded alias extent after native creation succeeds. An optional result-producing release callback keeps existing Windows/Linux action callback semantics intact. The provider captures actual alias-unmap and descriptor-close results separately. Failed munmap has an uncertain native outcome and retains both logical cleanup obligations without repeating the syscall. No unchanged/survivor receipt exists here to authorize a retry. Successful munmap followed by failed close leaves descriptor outcome unknown: POSIX descriptor reuse forbids blindly retrying close, so this state stays quarantined.

Ordinary balanced access admission linearizes with close on one atomic count/closing word. Mapping and alias copy callers participate; there is no new signal API or allocation per alias copy. Disposal closes admission before native release, drains outside backing and view gates, and revalidates the one active release attempt before invoking the provider callback. Timeout closes admission but retains storage for a later cleanup attempt. Release callback failure cannot fake completed disposal.

SharedBackingViews revokes/publishes its empty access snapshot under its own lock and captures remaining view cleanup. Cleanup runs outside that lock; failed unmaps retain exact remaining records in quarantine, prevent backing release, and never repeat an uncertain native operation. Only a timeout before native effects is retryable. GuestSpaceOwner disposal captures/revokes under mapping/protection gates and drops them before view drain/release. Successful owned-range releases are removed individually so retries do not reclaim an address already released and possibly reused by the OS.

This does not complete PVM/Kernel outer transaction participation, per-view MAP_FIXED identity, base permission/watcher cohorts, direct tracker mprotect, or signal disposition during close. Those remain prerequisites for Poppy recovery. No native memory execution is implied by managed controls.

Normal PVM Dispose calls Clear, whose locks exit before GuestSpaceOwner.Dispose; it does not hold PVM gates during alias drain. Clear still mutates guest view mappings under those gates, with no new alias drain in this increment. Reentrant caller-held PVM locks are not certified. Map/unmap use a bounded ordinary pending-operation reservation; provider calls hold no view/cleanup gate. Disposal requests close then waits for pending completion outside the gate (Monitor.Wait releases the only owned gate). A provider callback on the pending owner's thread cannot wait for itself: reentrant Dispose records close request and returns with CleanupComplete=false. The outer map rolls back its exact successful late view, releases the reservation, then completes requested disposal before returning; exception paths retain attempted scope/primary error with secondary cleanup context instead. A concurrent disposer waits bounded for actual completion or quarantine. Fresh public same-thread map/unmap requests after close are rejected; only private rollback/restoration continuations of the already admitted transaction may finish. This ordinary deferred seam does not qualify signal reentrancy.

Raw AliasBase/Handle/Descriptor properties remain trusted backend/ordinary caller contracts. They do not issue a reservation. The production Vulkan cached-alias consumer enters alias access around ProcessOne and exits in finally; PVM forwards Exit to the backing owner until successful disposal returns, then nulls it. All SharedBackingViews clear/read/write/copy and explicit alias access paths participate. External unmanaged writes/content publication, direct guest virtual access, shared view remaps, and explicit native syscall bypass remain unqualified.
