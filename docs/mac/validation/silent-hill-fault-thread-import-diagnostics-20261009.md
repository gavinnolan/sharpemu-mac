## Independent diagnostic defect and narrow change

The legacy backend ring explicitly excludes guest workers and fast paths. The actual fault dump labels its heading with thread 67 but prints 64 entries from managed thread 4. It cannot establish RHI history. Moreover, hot/trivial/leaf dispatch returns before the existing active guest `LastImport` snapshot is updated. `V++UgBtQhn0` is explicitly a trivial/leaf import, so the recorded `n2fD4A+pb+g` may remain after the payload helper ran; it is the last recorded general-dispatch import, not necessarily the last actual import.

Cached default-off `SHARPEMU_FAULT_THREAD_IMPORT_DIAGNOSTICS=1` wraps the unchanged dispatcher core. Only the enabled route allocates a 64-entry managed-thread-local ring and records index, NID and exact backend ownership before all fast dispatch paths. No trusted readable argument-frame extent is available at this point. The diagnostic helper never dereferences the argument pack; arguments and return RIP are explicitly not observed. Only the unchanged dispatcher core performs its original reads, including the three-qword hot memcpy/memmove path. It calls the original core once, returns its exact ulong, records `Returned` with that exact value or `Threw` without a return, and leaves still-active faulting entries as `Entered`/not observed. A returned zero/error is never classified as success. Local sequence is explicitly distinct from the global dispatch index. Nested eviction cannot complete a younger slot as an old return; first completion cannot be replaced. Fault snapshots select actual managed and guest thread identity plus the exact active backend object (falling back to the caller backend only when none is active). This prevents two backends on the same host thread, including guest handle zero, from being presented as one history. Optional allocation/snapshot/output failures cannot replace dispatch or fault policy. The old ring is retained with an explicit legacy label; existing last-import output is marked general-dispatch-only.

Fifteen ordinary metadata controls cover zero and unknown returns, exact first completion, nested eviction, managed/guest filtering, foreign owner refusal, two actual managed threads' independent helper rings, and the actual enabled helper's trivial fast return/throw/no-context/invalid-index paths. A separate actual hot memcpy helper control supplies only three managed qwords with count zero and checks the unchanged return, no export call, unchanged pack and preserved memory failure; this is a source-level managed control, not native guard-page proof. Exact backend filtering is tested with both records on one managed thread and guest handle zero. The helper fixture uses a managed pinned argument pack, an uninitialized backend and a synthetic export. It allocates no native TLS, executes no guest/native entry and starts no worker. It preserves an actual `TrackedCpuMemory.LastFailure`. Mutable thread-local control state is saved/restored; the cached flag and readonly fields are untouched. These controls test the production enabled helper directly without claiming startup flag activation or native execution.
